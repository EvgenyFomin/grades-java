# 6. Файловые дескрипторы и стандартные потоки

## Что такое файловый дескриптор (fd)

Программа почти никогда не работает с файлом напрямую — она работает с **файловым дескриптором** (file descriptor, fd): просто целым числом, которое ядро выдало при открытии. Внутри ядро по этому числу находит таблицу открытых файлов процесса.

```
fd 0 ---->  /dev/pts/0  (терминал, stdin)
fd 1 ---->  /dev/pts/0  (терминал, stdout)
fd 2 ---->  /dev/pts/0  (терминал, stderr)
fd 3 ---->  /home/user/file.txt
fd 4 ---->  socket (TCP-соединение)
```

Десриптор — это «ручка» (handle). Все операции — `read()`, `write()`, `close()`, `fsync()` — в syscall'ах передают именно число-дескриптор, а не путь к файлу. Путь нужен только один раз — на `open()`; дальше ядро работает с дескриптором.

Последовательность для обычного файла:

```text
open("/etc/hostname") -> fd 3        (ядро заводит запись в таблице)
read(3, buf, 4096)                   (читаем через дескриптор)
write(3, "hello", 5)                 (пишем через дескриптор)
close(3)                             (освобождаем дескриптор)
```

## Откуда берётся дескриптор

Дескриптор возвращают системные вызовы, создающие «файл»:

| Syscall | Что открывает | Возвращает |
| --- | --- | --- |
| `open()`, `creat()` | файл, устройство | fd |
| `socket()` | сетевое соединение | fd |
| `pipe()` | анонимный канал | 2 fd (чтение + запись) |
| `accept()` | входящее TCP-соединение | новый fd |
| `dup()` / `dup2()` | копию существующего fd | новый fd |

Ключевой момент: раз сокеты и пайпы тоже представлены дескрипторами (см. п. 5 «Всё — файл»), единый интерфейс `read()/write()` работает со всем одинаково. Для ядра «записать в файл» и «отправить байты в сокет» — одна и та же операция `write(fd, ...)`, просто за разными fd стоит разный код.

## Таблица файловых дескрипторов процесса

У каждого процесса своя таблица fd. Это **число** — индекс в этой таблице. Ключевые свойства:

- Дескрипторы нумеруются с 0. Новый открытый файл получает **наименьший свободный номер**.
- Таблица **персональная**: дескрипторы одного процесса недоступны другому. Наследуются только при `fork()` (потомок получает копию таблицы).
- Размер таблицы ограничен лимитом `ulimit -n` (обычно 1024 в Bash, у systemd-сервисов часто больше).

Посмотреть таблицу текущего процесса:

```bash
ls -l /proc/self/fd/
```

Ожидаемый вывод (у шелла всегда открыты минимум 0, 1, 2 — стандартные потоки):

```
lrwx------ 1 user user 64 aug 16 09:00 0 -> /dev/pts/0
lrwx------ 1 user user 64 aug 16 09:00 1 -> /dev/pts/0
lrwx------ 1 user user 64 aug 16 09:00 2 -> /dev/pts/0
```

Символические ссылки в `/proc/<pid>/fd/` показывают, «куда ведёт» каждый дескриптор. Это самый наглядный способ увидеть, что держит открытым процесс (включая сокеты и пайпы).

## Стандартные потоки: stdin, stdout, stderr

Любой процесс при запуске получает три готовых дескриптора:

| № | Имя | Направление | По умолчанию | Что пишут/читают |
| --- | --- | --- | --- | --- |
| 0 | `stdin` | чтение | терминал | данные на вход программы |
| 1 | `stdout` | запись | терминал | обычный вывод |
| 2 | `stderr` | запись | терминал | ошибки и диагностика |

В `bash` `/dev/pts/0` — это терминал (виртуальный). Для демонов и сервисов systemd стандартные потоки по умолчанию ведут в `/dev/null`, а их можно переопределить юнитом (п. 13).

Важно: **stderr существует отдельно от stdout**. Это сделано намеренно — ошибки не должны перемешиваться с данными, особенно если данные перенаправлены в файл или конвейер.

## Перенаправление (redirection)

Перенаправление — это подмена дескриптора на другой «файл» перед запуском команды. Раз stdin/stdout/stderr — дескрипторы, их можно переключить на файл, пайп или сокет. Делает это шелл через `dup2()`, поэтому для самой программы ничего не меняется: она по-прежнему пишет в fd 1, но fd 1 теперь ведёт в файл.

### Запись в файл: `>` и `>>`

```bash
echo "hello" >  log.txt    # stdout (1) -> log.txt, файл перезаписывается
echo "more"  >> log.txt    # stdout (1) -> log.txt, дописывание в конец
```

- `>` — создать/перезаписать файл, открыть на запись (`O_WRONLY|O_CREAT|O_TRUNC`).
- `>>` — создать/дописать (`O_WRONLY|O_CREAT|O_APPEND`).

### Чтение из файла: `<`

```bash
wc -l < log.txt            # stdin (0) <- log.txt
```

### Ошибки: `2>` и `2>>`

```bash
grep foo file 2> err.log   # только stderr -> файл
grep foo file 2>> err.log  # stderr -> файл (дописать)
```

### Всё вместе: `&>` и `&>>`

```bash
command > out.txt 2>&1     # stdout в файл, затем stderr направить туда же
command &> out.txt         # то же самое, краткая запись (stdout + stderr)
command &>> out.txt        # то же, но дописывание
```

`2>&1` — не магия, а честное перенаправление дескриптора: «сделать так, чтобы fd 2 указывал туда же, куда сейчас указывает fd 1». Порядок важен: `> out.txt 2>&1` сначала перенаправляет 1 в файл, потом 2 за 1. Если написать `2>&1 > out.txt` — сначала 2 уйдёт в текущий stdout (терминал), и только потом 1 — в файл, ошибки останутся на экране.

### Порядок операций: пример с JVM

```bash
java -jar app.jar > app.log 2>&1    # весь вывод и ошибки — в app.log
java -jar app.jar 2> err.log        # только ошибки JVM — в err.log
```

## Конвейеры: `|`

Оператор `|` соединяет stdout одной команды со stdin другой через **анонимный пайп** (п. 10):

```bash
ls -la | grep -c '^d'
# stdout команды ls -> пайп -> stdin команды grep
```

Фактически шелл создаёт пайп, направляет fd 1 первой команды на запись в пайп, а fd 0 второй — на чтение из пайпа. Команды выполняются **параллельно**, буферизация идёт через буфер ядра.

У стderr в конвейере **своя судьба**: он не передаётся дальше по умолчанию. Ошибки первой команды пойдут на терминал:

```bash
ls /nonexistent | cat    # ошибка "No such file..." печатается в терминал, не в cat
```

Чтобы объединить и передать дальше ошибки: `ls /nonexistent 2>&1 | cat`.

## Подмена дескрипторов: `exec`

`exec` в Bash умеет менять дескрипторы **текущего** шелла (не запускает новую команду). Это полезно для сценариев:

```bash
# Направляем весь дальнейший вывод скрипта в файл
exec > script.log 2>&1

# Открыть файл как новый дескриптор fd 3
exec 3> file.txt
echo "text" >&3
exec 3>&-            # закрыть fd 3

# Перенаправить только на время
exec 3>&1            # сохранить текущий stdout в fd 3
echo "to terminal"   # идёт на терминал
exec 1> file.txt     # теперь stdout — файл
echo "to file"
exec 1>&3            # вернуть stdout обратно
```

## Перенаправление на уровне ядра (dup2)

Всё, что делает шелл, в конечном счёте — syscall `dup2(old_fd, new_fd)`: он делает так, чтобы `new_fd` указывал на тот же объект, что и `old_fd`. Например, `2>&1` — это `dup2(1, 2)`: «сделай fd 2 копией fd 1». После этого записи в 2 идут в тот же файл/пайп/терминал, что и записи в 1.

В системном вызове перенаправление с экраном программы выглядит так:

```bash
strace -f -e trace=dup2 bash -c 'ls > out.txt 2>&1'
# ...
# dup2(1, 2)            <- 2>&1: stderr идёт туда же, куда stdout
# dup2(3, 1)            <- > out.txt: новый fd из open() становится stdout
# close(3)
# execve("/usr/bin/ls", ...)
```

## /dev/null и /dev/fd

```bash
# /dev/null — «чёрная дыра»: запись исчезает, чтение даёт EOF
command > /dev/null 2>&1

# /dev/fd/N — ещё один способ сослаться на дескриптор
echo "hello" > /dev/fd/1
```

`/dev/null` часто используется, чтобы отбросить вывод; `/dev/fd/N` — чтобы передать открытый дескриптор туда, где ожидается имя файла.

## Как это связано с Java

JVM использует те же стандартные потоки:

- `System.out` — fd 1, `System.err` — fd 2, `System.in` — fd 0.
- При запуске из терминала/шелла они указывают на терминал или перенаправление; при запуске под systemd — на `/dev/null` или лог-файл (п. 13).
- Любой `FileInputStream`/`FileOutputStream` внутри JVM — это дескриптор: JVM вызывает `open()` и хранит fd, а `read()`/`write()` идут по нему (п. 9).
- Перенаправление из шелла работает и для Java: `java App < in.txt > out.txt 2> err.txt`.

Посмотреть, какие дескрипторы держит Java-процесс, можно так:

```bash
ls -l /proc/$(pgrep -f 'java App')/fd/
```

## Практика

```bash
# 1. Стандартные потоки текущего шелла
ls -l /proc/self/fd/

# 2. Запись с перезаписью и дописыванием
echo "first"  >  log.txt
echo "second" >> log.txt
cat log.txt               # обе строки

# 3. Разделение stdout и stderr
ls /etc /nonexistent 1> ok.txt 2> err.txt
cat ok.txt                # только существующий каталог
cat err.txt               # только ошибка

# 4. Всё в один файл
ls /etc /nonexistent > all.txt 2>&1
cat all.txt

# 5. Конвейер с ошибками
ls /nonexistent | cat               # ошибка видна в терминале
ls /nonexistent 2>&1 | cat          # ошибка уходит в конвейер

# 6. Подмена дескрипторов в скрипте
exec > script.log 2>&1
echo "это уйдёт в файл"
exec 3>&1 && echo "восстановлено" >&3

# 7. Наследование fd при запуске программы
exec 3> extra.txt
bash -c 'echo "через унаследованный fd" >&3'
exec 3>&-
```

## Связь со следующими разделами

- Дескрипторы — это «числовые имена» сущностей из п. 5 («Всё — файл»): файлов, сокетов, пайпов, `/proc`.
- `read()`/`write()` по дескриптору — те самые syscall'ы из п. 3 (user/kernel mode), которые обсуждаются в п. 9.
- Анонимный пайп в конвейере `|` подробно разобран в п. 10 (pipes и FIFO).
- `/proc/<pid>/fd` и `/proc/<pid>/io` — п. 11 (виртуальные ФС).
- systemd может переопределять stdin/stdout сервисов (п. 13).
