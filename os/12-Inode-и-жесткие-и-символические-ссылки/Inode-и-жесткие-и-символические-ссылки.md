# 12. Inode, hard/soft links

## Проблема: имя файла ≠ сами данные

Файл в Linux — это не «кусок диска с именем». Имя — всего лишь запись в директории, а данные живут в структуре ядра, которая называется **inode**. Один inode может иметь несколько имён, а имя может «указывать» на inode через цепочку. Разберёмся, что происходит при `open()`, `rm`, `cp` и `mv`, и почему бывают ссылки.

```
┌────────────────────┐        ┌────────────────────────────┐
│  Директория        │  имя → │  Inode (ядро)              │
│  dentry:           │ ─────► │  - права, владелец          │
│  "file.txt" → #42  │        │  - размер                   │
│                    │        │  - время доступа/изменения  │
│                    │        │  - список блоков на диске   │
│                    │        │  - счётчик ссылок (nlink)   │
└────────────────────┘        └────────────────────────────┘
```

Ключевая идея: **директория хранит не данные, а таблицу «имя → inode»**. Отсюда вытекают все свойства ссылок.

## 1. Что такое inode

Inode — это запись в таблице inode файловой системы, описывающая объект: права доступа, владельца, размер, временные метки и адреса блоков на диске. Именно его видит команда `stat`:

```bash
stat /etc/hostname
  File: /etc/hostname
  Size: 10            Blocks: 8          IO Block: 4096   regular file
Device: 8,1   Inode: 786658      Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
...
```

Полезные поля:

| Поле | Что означает | Связь с планом |
| --- | --- | --- |
| **Inode** | номер inode — уникальный идентификатор объекта в ФС | `stat -c %i`, `ls -li` |
| **Links** | счётчик ссылок (nlink): сколько имён указывает на этот inode | тема hard links |
| **Size / Blocks** | размер в байтах и занятое место в блоках | тема I/O |
| **Device** | на каком устройстве (major:minor) лежит inode | п. 11, `/dev` |
| **Uid/Gid, Access** | права и владелец | п. 4 |

Директория — это тоже inode (типа `directory`), внутри которого список пар «имя → inode». Поэтому «создание файла» — это две операции: завести inode и добавить запись в директорию. Именно поэтому `rm` и `mv` не требуют прав на сам файл — достаточно прав на **директорию**.

Связь с п. 4 и п. 5: права, которые ядро проверяет при `open()`/`read()`/`write()`, хранятся в inode, а «всё — файл» означает, что и регулярный файл, и директория, и сокет, и FIFO (п. 10) имеют inode.

## 2. Hard links (жёсткие ссылки)

Жёсткая ссылка — это **ещё одно имя для того же inode**. Одно и то же содержимое существует один раз на диске, но к нему ведут два (или больше) имени.

```bash
echo "данные" > original.txt
ln original.txt hard_link.txt        # создать жёсткую ссылку

ls -li original.txt hard_link.txt    # ОДИН и тот же inode у обоих
123456 -rw-r--r-- 2 user user 7 ... original.txt
123456 -rw-r--r-- 2 user user 7 ... hard_link.txt
```

Что это значит:

- **Счётчик Links = 2**: один inode, два имени. Проверка: `stat -c %i:%h original.txt` → `123456:2`.
- Изменение через любое имя видно через другое — это буквально тот же объект.
- **Удаление файла** — это не «удаление данных», а уменьшение счётчика ссылок. Данные удаляются только когда `nlink` падает до 0. Отсюда вывод: `rm original.txt` не уничтожит данные, пока существует `hard_link.txt`.
- Создание жёсткой ссылки происходит внутри одной ФС: нельзя сделать hard link на другой диск или на другую файловую систему (`ln: failed to create hard link: Invalid cross-device link`).
- Нельзя создавать жёсткие ссылки на **директории** (это запрещено, чтобы не появились циклы), и на объекты, у которых нет обычного inode (некоторые виртуальные ФС из п. 11).

Практический смысл: жёсткие ссылки позволяют иметь файл «в двух местах», не дублируя данные — например, в Git объекты хранятся именно так. Обычный пользователь видит их как «один файл с двумя именами».

## 3. Soft links (символические ссылки, symlink)

Символическая ссылка — это **файл особого типа, внутри которого лежит путь к другому файлу**. Это отдельный inode (типа `symbolic link`), поэтому:

```bash
ln -s original.txt soft_link.txt     # создать символическую ссылку

ls -li original.txt soft_link.txt    # РАЗНЫЕ inode!
123456 -rw-r--r-- 2 user user 7 ... original.txt
654321 lrwxrwxrwx 1 user user 12 ... soft_link.txt -> original.txt
```

Что это значит:

- **Свой собственный inode** (номер 654321), поэтому `Links: 1` у самого symlink, а не у цели.
- Тип файла `l` (symbolic link), и в нём хранится **путь**: `original.txt` (относительный) или `/home/user/original.txt` (абсолютный).
- Может указывать на файл на **другой файловой системе** и даже на **несуществующий файл** (тогда говорят «битая ссылка», `ls` показывает `broken`).
- Если переместить или удалить цель — симлинк «разрывается». Он не защищает данные: `rm` симлинка удаляет только сам симлинк, а `rm` цели удаляет данные.

Как это работает при обращении:

```bash
cat soft_link.txt     # ядро читает содержимое симлинка: "original.txt",
                      # затем открывает original.txt
```

В `strace` видно цепочку `openat()` с флагом `O_PATH` и реальный путь:

```bash
strace -e openat cat soft_link.txt 2>&1 | grep openat
openat(AT_FDCWD, "soft_link.txt", O_RDONLY) = 3
openat(AT_FDCWD, "original.txt", O_RDONLY) = 3
```

## 4. Сравнение hard и soft links

| | **Hard link** | **Symlink (soft link)** |
| --- | --- | --- |
| Что это | второе имя того же inode | отдельный файл с путём |
| Номер inode | **тот же**, что у оригинала | **свой**, не тот же |
| В `ls -l` | обычный тип файла (`-`) | тип `l`, стрелка `->` |
| Размер | размер оригинала | длина пути |
| Можно ли между ФС | **нет** | да |
| На директории | нельзя | можно |
| На несуществующий файл | нельзя | можно (битая) |
| Если удалить оригинал | данные живут, пока есть ссылка | ссылка «разрывается» |
| Занимает место | нет (только запись в директории) | да (сам файл с путём) |
| Создание | `ln file link` | `ln -s file link` |

Краткое правило: **hard link — «ещё одно имя», symlink — «стрелка на имя»**.

## 5. Как ссылки ведут себя с реальными файлами

Проверка, что изменился только inode при копировании:

```bash
echo "текст" > a.txt
cp a.txt b.txt          # это НОВЫЙ inode (две копии данных!)
ln a.txt c.txt          # это тот же inode, что у a.txt

ls -li a.txt b.txt c.txt
111111 -rw-r--r-- 2 user user 6 ... a.txt   ← links: 2
222222 -rw-r--r-- 1 user user 6 ... b.txt   ← links: 1, новый inode
111111 -rw-r--r-- 2 user user 6 ... c.txt   ← тот же inode, что a.txt
```

`cp` создаёт **новый** inode и копирует данные, `ln` — просто добавляет имя к **существующему** inode. Поэтому у `cp` и `ln` разная цена: копия удваивает место, ссылка — нет.

## 6. Пример из реальной жизни

- `/bin/sh -> dash` — симлинк: пакеты могут обновлять dash, а `/bin/sh` всегда указывает на актуальный бинарник.
- `/proc/self/exe` (п. 11) — симлинк на исполняемый файл текущего процесса.
- Каталоги: у каждой директории есть «скрытые» записи `.` и `..` — это жёсткие ссылки на саму директорию и на родителя (поэтому у директории `Links ≥ 2`).

## Практика

```bash
# 1. Номера inode: у файла, у директории, у симлинка
ls -li /etc/hostname /tmp /bin/sh
stat -c '%i %h %n' /etc/hostname        # inode, links, имя

# 2. Создание и сравнение hard/soft links
echo hello > original.txt
ln original.txt hard_link.txt
ln -s original.txt soft_link.txt
ls -li original.txt hard_link.txt soft_link.txt

# 3. Что происходит при удалении оригинала?
rm original.txt
cat hard_link.txt        # данные на месте: inode жив
cat soft_link.txt        # ошибка: "No such file or directory" — битая ссылка

# 4. Счётчик ссылок через stat
stat -c 'inode=%i links=%h' hard_link.txt

# 5. Сколько hard-ссылок на каталог (должно быть >= 2: . и ..)
stat -c '%h %n' /tmp

# 6. Где в системе живут симлинки (связь с п. 11)
find /proc/self -maxdepth 1 -type l -ls | head
```

## Связь со следующими разделами

- Права из inode (п. 4) — это то, что проверяет ядро при открытии файла; hard/symlink'и не дают обойти права, ядро смотрит на владельца **целевого** inode.
- Типы `p` (FIFO, п. 10) и `c`/`b` (устройства, п. 11) — это тоже inode разных типов; `ls -l` показывает их по букве типа.
- Символические ссылки удобно наблюдать в `/proc`: `/proc/self/exe`, `/proc/self/cwd` — это symlink'и (п. 11).
- Жёсткие ссылки показывают, почему `rm` не всегда освобождает место: данные удаляются только при `nlink == 0`.
