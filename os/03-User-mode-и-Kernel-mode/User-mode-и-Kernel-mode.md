# 3. User mode и Kernel mode

## Два режима работы процессора

Современный процессор умеет работать в нескольких режимах с разными правами. Для понимания I/O достаточно двух из них:

- **User mode** — режим приложений. Здесь работают все ваши программы: Java-процесс, редактор, браузер. Приложение не имеет прямого доступа к устройствам, памяти ядра и большинству привилегированных инструкций.
- **Kernel mode** — режим ядра. Здесь работает сама ОС: управление памятью, планировщик, драйверы, файловые системы, сетевой стек. Код в этом режиме может обращаться к аппаратуре напрямую.

Переключение между режимами — не декоративная деталь, а **основной механизм защиты**: если приложение может выполнять любой код, оно может сломать всю систему. Поэтому пользовательские программы принципиально не могут «просто взять и записать байт на диск» — за них это делает ядро.

### Rings 0–3

На архитектуре x86 режимы оформлены как **кольца привилегий (protection rings)**:

| Ring | Кто работает | Что разрешено |
| --- | --- | --- |
| Ring 0 | Ядро ОС | Всё: прямое обращение к устройствам, спец. инструкции |
| Ring 1 | (не используется в Linux) | Промежуточный уровень |
| Ring 2 | (не используется в Linux) | Промежуточный уровень |
| Ring 3 | Пользовательские процессы | Ограниченный набор: обычные вычисления, обращения к памяти своего адресного пространства |

Linux использует только два кольца: **Ring 0** для ядра и **Ring 3** для пользовательских программ. Переход между ними — это и есть вход в режим ядра.

## Syscalls — мост между режимами

Раз приложение не может работать с устройствами напрямую, ему нужен **официальный канал** для запросов к ядру. Этот канал — **системные вызовы (syscalls)**.

Любая операция I/O в итоге сводится к одному или нескольким syscall'ам:

- чтение файла — `read()`
- запись — `write()`
- открытие/закрытие — `open()`, `close()`
- ожидание событий на сокетах — `epoll_wait()`
- создание потока — `clone()`

Как выглядит вызов на уровне машинных инструкций (упрощённо):

```
1. Приложение кладёт номер syscall'а в регистр (например, rax) и аргументы в другие регистры.
2. Выполняется привилегированная инструкция перехода в ядро (syscall / int 0x80).
3. Процессор переключается в kernel mode, ядро выполняет операцию от имени процесса.
4. Ядро возвращает результат и переключает процессор обратно в user mode.
```

С точки зрения Java-программиста этого почти не видно: вы вызываете `FileInputStream.read()`, а под капотом JVM делает syscall `read()` на файловом дескрипторе. Детально это разбирается в п. 9.

### Какие операции требуют syscall'а, а какие нет

- **Нужен syscall**: чтение/запись файлов и сетей, создание процессов и потоков, выделение памяти у ядра (`mmap`), доступ к времени, ввод с клавиатуры.
- **Не нужен**: чисто вычислительный код (математика, работа с данными в RAM) — он выполняется полностью в user mode, без переключения режимов.

Именно поэтому «вычисление в памяти» работает на порядки быстрее «чтения файла»: операция в user mode не платит за переключение режимов и не ждёт ядро.

## Связь kernel mode и системы привилегий

Привилегии на файлах (права `rwx`, setuid, sticky bit) проверяются именно в **kernel mode**: каждый раз, когда приложение делает `open()`, ядро сверяет права процесса с правами файла и решает, пускать или вернуть `Permission denied`. Приложение само не может обойти эту проверку — у него нет прав влиять на решение ядра.

Сами «специальные биты» (`rws`, sticky bit) — это флаги в метаданных inode, которые ядро интерпретирует при выполнении программ и доступе к файлам/директориям. Как именно работают эти флаги — разобрано в п. 4 «Система привилегий в Linux».

## Почему это важно для понимания I/O

- Каждое переключение режима — это **стоимость**: сохранение/восстановление контекста, проверка прав, планировщик. Модели I/O (блокирующие, неблокирующие, асинхронные) — это по сути разные способы платить эту стоимость и не простаивать зря (п. 9).
- Ошибки уровня «доступ запрещён» (`Permission denied`) — следствие разделения режимов: ядро отказывает приложению в операции, на которую у него нет прав.
- `strace` показывает, какие syscall'ы делает ваша программа, — а значит, показывает **реальную границу между user mode и kernel mode** на практике.

## Практика

Посмотрите, сколько syscall'ов делает обычный процесс и каких именно:

```bash
# Запустить программу и по завершении посчитать статистику syscall'ов
strace -c ls /tmp

# Пример вывода:
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  30.00    0.001200       1200         1          1 read
#  15.00    0.000600        600         1          1 write
# ...
```

Полезные вариации:

```bash
# Статистика syscall'ов Java-процесса (запустите свой класс вместо Sample)
strace -c java Sample

# Живой вывод каждого syscall'а (длинно, но наглядно)
strace ls /tmp

# Только syscall'ы на конкретном дескрипторе
strace -e read,write,close cat /etc/hostname
```

## Связь со следующими разделами

- Syscall'ы — это то, через что работает концепция «Всё — файл» (п. 5): всё открывается через `open()`, читается через `read()`.
- Файловые дескрипторы — аргументы этих syscall'ов (п. 6).
- Проверку прав при каждом `open()`/`read()`/`write()` делает ядро — подробно в п. 4 (система привилегий).
- `clone()` под капотом создания Java-потоков (п. 7).
- Как планировщик переключает потоки и что при этом сохраняется — п. 8.
- `read` / `write` / `epoll_wait` / `io_uring_enter` — syscall'ы моделей I/O (п. 9).
