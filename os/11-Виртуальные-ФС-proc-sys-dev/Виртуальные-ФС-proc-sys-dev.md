# 11. Виртуальные ФС: `/proc`, `/sys`, `/dev`

## Проблема: как «спросить» ядро о его состоянии

Обычная файловая система хранит данные на диске. Но у ядра Linux есть состояния, которые программам постоянно нужно читать и менять: сколько CPU потребляет процесс, какие дескрипторы у него открыты, какие устройства подключены, сколько памяти свободно. Это не файлы на диске — это **внутренние структуры ядра**.

Решение — виртуальные файловые системы: `/proc`, `/sys`, `/dev`. Они существуют только в памяти, но выглядят как обычные файлы и директории. «Всё — файл» из п. 5 работает в обе стороны: файловый интерфейс для **любых данных ядра**. Читаешь файл — ядро «на лету» собирает ответ; пишешь в файл — ядро меняет свою конфигурацию.

```
┌──────────────┐   read/write на «файлы»    ┌──────────────────────────────┐
│  программы   │ ─────────────────────────► │  /proc /sys /dev (в памяти)  │
│  cat, stat,  │                            │        └──►  ядро            │
│  ls /proc/1  │ ◄───────────────────────── │  ответ формируется на лету    │
└──────────────┘        данные ядра          └──────────────────────────────┘
```

Никакого диска за ними нет: `du -sh /proc` покажет малую величину, а `df` — отдельную «монтированную» ФС типа `proc`/`sysfs`/`devtmpfs`.

## Что и где лежит

| ФС | Содержимое | Пример |
| --- | --- | --- |
| **`/proc`** (procfs) | данные **процессов** и ядра: `/proc/<pid>/...`, `/proc/cpuinfo`, `/proc/meminfo`, `/proc/interrupts` | `/proc/self/fd`, `/proc/1/cmdline` |
| **`/sys`** (sysfs) | **устройства** и драйверы, конфигурация ядра | `/sys/class/net/eth0/`, `/sys/block/` |
| **`/dev`** (devtmpfs/udev) | **узлы устройств**: точки входа в драйверы, типы `b`/`c` | `/dev/sda`, `/dev/null`, `/dev/tty` |

Разница подходов: `/proc` отдаёт «моментальный снимок» состояния в виде текста, `/sys` — иерархию устройств как дерево директорий с атрибутами, `/dev` — файлы-«двери» к драйверам. Если надо узнать об устройстве — иди в `/sys`; если про процесс — в `/proc`.

## 1. `/proc/<pid>/`: цифры процессов

Для каждого запущенного процесса ядро создаёт директорию с именем его PID. В ней — файлы-«окна» во внутренности процесса:

```
/proc/1/              ← процесс с PID 1 (systemd)
├── cmdline           ← командная строка процесса
├── cwd               ← симлинк на рабочую директорию
├── exe               ← симлинк на исполняемый файл
├── status            ← статус, приоритет, память (текст)
├── io                ← сколько байт прочитано/записано (I/O!)
├── fd/               ← открытые файловые дескрипторы (см. п. 6)
└── ...
```

**`/proc/<pid>/io`** — ключ к теме ввода/вывода: ядро считает для процесса количество прочитанных и записанных байт через syscall'ы `read()`/`write()`:

```bash
cat /proc/self/io     # чтение собственного I/O процесса cat
rchar: 1633           # байт прочитано через read()
wchar: 0              # байт записано через write()
syscr: 4              # число системных вызовов read()
syscw: 0              # число системных вызовов write()
read_bytes: 0         # реально прочитано с диска (без кеша)
write_bytes: 0        # реально записано на диск
```

Обратите внимание на разницу: `rchar`/`wchar` считают все байты, прошедшие через `read()`/`write()`, а `read_bytes`/`write_bytes` — только те, что дошли до **реального диска** (минуя page cache). Поэтому во время чтения из кеша `rchar` растёт, а `read_bytes` — нет.

**`/proc/<pid>/fd/`** — открытые дескрипторы (связь с п. 6):

```bash
ls -l /proc/self/fd/
lrwx------ 1 user user 64 ... 0 -> /dev/pts/0    # stdin — терминал
lrwx------ 1 user user 64 ... 1 -> /dev/pts/0    # stdout — терминал
lrwx------ 1 user user 64 ... 2 -> /dev/pts/0    # stderr — терминал
```

Видно то же, что показывает `strace`: дескрипторы 0, 1, 2 и их цели. Сюда же попадают дескрипторы pipe из п. 10 (`pipe:[номер]`) и сокеты из п. 13/14 курса.

Полезные трюки с `/proc`:

- `/proc/self` — всегда директория текущего процесса, удобно для проверок «изнутри».
- `/proc/uptime`, `/proc/meminfo`, `/proc/cpuinfo`, `/proc/loadavg` — сводки о системе (это их читают `uptime`, `free`, `top`).
- `/proc/sys/` — настройки ядра, которые можно менять на лету (например, `/proc/sys/kernel/hostname`). Это же видно в `/sys`.
- `/proc/interrupts` — как часто срабатывают аппаратные прерывания (связь с п. 8 — прерывания таймера).

## 2. `/sys`: дерево устройств и драйверов

`/sys` показывает **всё, что ядро знает об устройствах**, как дерево директорий. Каждая директория — устройство или класс устройств, каждый файл — один атрибут.

```bash
/sys/class/net/eth0/
├── address          # MAC-адрес сетевой карты
├── mtu              # размер кадра
├── speed            # скорость линка
├── statistics/      # счётчики пакетов
└── operstate        # up / down
```

Работа с атрибутами — обычные `read`/`write`:

```bash
cat /sys/class/net/eth0/address     # прочитать MAC
echo 9000 > /sys/class/net/eth0/mtu # поменять MTU (правда, только от root)
```

Отличие от `/proc`: `/sys` — не «список» значений, а **модель устройств**: откуда устройство, какие у него драйверы, в каком классе оно состоит. Пара важных точек:

- `/sys/block/sda/` — диски, `/sys/class/` — устройства по назначению (net, tty, gpu, input...).
- Многие значения здесь дублируют `/proc`: `/proc/partitions` ≈ `/sys/block/*/size`.
- Правило: `/proc` — «что делает система сейчас», `/sys` — «как устроены устройства и как их настраивать».

## 3. `/dev`: файлы-устройства (типы `b` и `c`)

`/dev` — это каталог **узлов устройств**: файлов, за которыми стоит драйвер. Когда приложение читает/пишет в `/dev/...`, syscall'ы `read()`/`write()` уходят в драйвер ядра.

```bash
ls -l /dev/sda /dev/null /dev/tty0
brw-rw---- 1 root disk  8, 0 ... /dev/sda     # b = block-устройство (диски)
crw-rw-rw- 1 root root  1, 3 ... /dev/null    # c = char-устройство (посимвольный обмен)
crw--w---- 1 root tty   4, 0 ... /dev/tty0    # c = терминал
```

Два типа узлов:

| Тип | Буква | Примеры | Как работают |
| --- | --- | --- | --- |
| **Block** | `b` | `/dev/sda`, `/dev/nvme0n1` | обмен блоками (обычно с диском), через буферы |
| **Character** | `c` | `/dev/tty`, `/dev/null`, `/dev/random` | посимвольный/поточный обмен, часто нет блочной структуры |

Важно: тип узла — это **интерфейс** к драйверу, а не обязательная физическая сущность. `/dev/null` не имеет диска — это «устройство» ядра, которое принимает данные и выбрасывает их (классический приём: `echo 1 > /dev/null 2>&1` для тихого игнорирования вывода).

Созданием узлов и подпиской устройств занимается **udev**: он смотрит на события от ядра и сам создаёт/удаляет файлы в `/dev`. Поэтому файлы здесь появляются «сами», когда устройство подключено.

## Практика

```bash
# 1. Что за файловые системы висят на /proc, /sys, /dev?
df -h /proc /sys /dev
mount | grep -E 'proc|sysfs|devtmpfs'

# 2. I/O процесса: сколько прочитано/записано (п. 9 — syscall'ы)
cat /proc/self/io
# следим за живым процессом (например, запущенным дольше):
cat /proc/$(pgrep -u $USER sshd | head -1)/io 2>/dev/null || cat /proc/1/io

# 3. Открытые дескрипторы любого процесса
ls -l /proc/1/fd | head           # у systemd всегда открыты некоторые fd
ls -l /proc/self/fd               # у текущего шелла

# 4. Информация о CPU и памяти
head -n 5 /proc/cpuinfo
head -n 5 /proc/meminfo

# 5. Устройства: увидеть типы b и c
ls -l /dev/sda /dev/null /dev/random /dev/tty0

# 6. Сеть через /sys
cat /sys/class/net/lo/address
cat /sys/class/net/lo/operstate

# 7. Интерактивный просмотр
watch -n 1 'cat /proc/self/io'    # обновляется раз в секунду
```

## Связь со следующими разделами

- `/proc/<pid>/fd` показывает открытые файловые дескрипторы из п. 6, включая pipe из п. 10.
- Счётчики `/proc/<pid>/io` — это результат работы syscall'ов `read()`/`write()` из п. 9.
- `/dev`, `/sys` — «файлы», у которых за inode стоит ядро (типы `b`/`c`, см. п. 12 про inode и link'и).
- Hard/soft link'и из п. 12 хорошо видны в `/proc`: `/proc/self/exe` — симлинк на запущенную программу, `/proc/self/cwd` — на рабочую директорию.
