# 4. Концепция «Всё — файл»

## Идея

В Unix/Linux **всё — файл**. Это значит, что любая сущность, с которой работает ОС, открывается одним и тем же способом — через `open()` — и читается/пишется через единый интерфейс `read()`/`write()`. Дальше ядро само разбирается, с чем именно работает программа:

- с обычным файлом на диске,
- с директорией,
- с сетевой картой (сокетом),
- с каналом между процессами (pipe),
- с терминалом,
- с устройством (диском, USB, звуковой картой),
- с данными, которые генерирует само ядро (`/proc`, `/sys`).

Для приложения интерфейс один и тот же. Отличается только тип файла и то, что за ним стоит.

## Файл — это абстракция

За единым интерфейсом стоит слой **VFS (Virtual File System)** — виртуальная файловая система ядра. VFS — это «фасад»: она принимает syscall от приложения (`open`, `read`, `write`, `stat`...) и перенаправляет его в конкретную реализацию:

| Что открыли | Кто реально обрабатывает запрос |
| --- | --- |
| `/home/user/file.txt` | драйвер `ext4` (реальная ФС на диске) |
| `/proc/self/status` | процедуры псевдо-ФС `procfs` (генерируют данные на лету) |
| `/sys/class/...` | псевдо-ФС `sysfs` (конфигурация и состояние устройств) |
| сокет | сетевой стек ядра |
| пайп | механизм каналов ядра |
| `/dev/sda` | драйвер блочного устройства |

VFS скрывает детали реализации. Именно поэтому концепция и называется «всё — файл»: даже вещи, которые файлами не являются (сетевое соединение, поток данных от процесса), выглядят как файлы.

## Типы файлов

Первый символ в `ls -l` показывает тип:

| Символ | Тип | Что это |
| --- | --- | --- |
| `-` | regular | обычный файл с данными |
| `d` | directory | директория |
| `l` | symlink | символическая ссылка |
| `p` | FIFO (pipe) | именованный канал |
| `s` | socket | сокет |
| `b` | block device | блочное устройство (диск) |
| `c` | char device | символьное устройство (терминал, звук) |

Проверка типа на практике:

```bash
ls -l /etc/hostname        # - regular
ls -ld /var               # d directory
ls -l /dev/null           # c char device
ls -l /dev/sda            # b block device
ls -l /var/run/docker.sock # s socket
```

`stat` показывает метаданные файла независимо от типа — размер, права, владельца, inode, время изменения:

```bash
stat /etc/hostname
#   File: /etc/hostname
#   Size: 10              Blocks: 8          IO Block: 4096   regular file
#   Device: 10304h/66564d Inode: 7609859     Links: 1
#   ...
```

Обратите внимание: у файла есть **inode** — внутренний номер, по которому ФС обращается к содержимому (подробнее — п. 12).

## `/proc` и `/sys` — файлы, которых нет на диске

Самые наглядные примеры «всё — файл» — псевдо-файловые системы:

- `/proc` — это **виртуальный образ процессов и данных ядра**. Каждый процесс представлен директорией `/proc/<pid>/`, внутри которой — файлы с его состоянием: `status`, `maps`, `io`, `fd`. Читать их можно как обычные файлы.
- `/sys` — интерфейс к **устройствам и драйверам**: `ls /sys/class/` покажет классы устройств (сеть, блок, звук...).

```bash
# Что внутри «директории» процесса?
ls -l /proc/self/fd/

# Сеть — тоже файлы
cat /proc/net/tcp

# Информация о CPU — файл
cat /proc/cpuinfo

# Состояние конкретного процесса
cat /proc/$$/status
```

Файлы `/proc` и `/sys` не занимают места на диске — содержимое генерируется ядром в момент чтения. Раздел подробнее разобран в п. 11.

## Что это даёт на практике

- **Универсальный инструментарий**: `cat`, `less`, `echo`, `cp`, `stat` работают с чем угодно — файлами, `/proc`, устройствами — потому что всё это файлы.
- **Единый интерфейс в коде**: один и тот же `read()`/`write()` работает и с файлом, и с сокетом. JVM использует это: `FileInputStream` и `SocketChannel` под капотом — одни и те же syscall'ы на дескрипторах.
- **Диагностика**: `/proc/<pid>/fd` показывает все открытые программой «файлы» — включая сокеты и пайпы. Это прямой способ увидеть, что процесс держит открытым.
- **Перенаправление** (п. 6): раз stdin/stdout/stderr — тоже файлы, их можно подменять на другие файлы, пайпы или сокеты.

## Практика

```bash
# 1. Все открытые «файлы» текущего шелла: 0=stdin, 1=stdout, 2=stderr
ls -l /proc/self/fd/

# 2. У каждого процесса свои открытые файлы
ls -l /proc/1/fd/ | head -20   # systemd
ls -l /proc/$$/fd/             # текущий шелл

# 3. stat для разных типов файлов — тип виден в первой строке вывода
stat /etc/hostname   # regular file
stat /dev/null       # character special file
stat /tmp            # directory

# 4. Проверить, что «устройство» читается как файл
head -c 100 /dev/urandom | xxd | head

# 5. Сеть как файл: прочитать информацию о соединениях
cat /proc/net/tcp | head
```

Ожидаемый результат первого пункта:

```
lrwx------ 1 user user 64 aug 16 09:00 0 -> /dev/pts/0   (stdin, терминал)
lrwx------ 1 user user 64 aug 16 09:00 1 -> /dev/pts/0   (stdout)
lrwx------ 1 user user 64 aug 16 09:00 2 -> /dev/pts/0   (stderr)
lr-x------ 1 user user 64 aug 16 09:00 3 -> /usr/lib/... (открытый файл)
```
