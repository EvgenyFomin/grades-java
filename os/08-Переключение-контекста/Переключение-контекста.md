# 7. Переключение контекста и планирование потоков

## Проблема: много потоков, мало ядер

В системе одновременно работают тысячи потоков (Java-приложения, системные процессы, ваша оболочка), а ядер процессора — всего несколько. Ядро должно решить, **какой поток выполнять прямо сейчас и на каком ядре**, и уметь **прерывать** поток, когда его время истекло. Этим занимается **планировщик**.

Планировщик работает в kernel mode и невидим для приложений: потоки думают, что выполняются «непрерывно», хотя на самом деле каждому из них достаётся лишь короткий срез времени (квант, обычно миллисекунды).

## Как планировщик выбирает поток

В Linux планировщик потоков — **CFS** (Completely Fair Scheduler).

- Каждому потоку выделяется **квант времени** — сколько он может выполняться, пока его не прервёт ядро.
- Учёт ведётся по **виртуальному времени**: чем меньше поток «наработал», тем скорее он получит следующий квант. Так все потоки делят CPU «по-честному».
- **Вытеснение (preemption)**: поток не обязан сам отдавать CPU. Когда квант исчерпан, **прерывание таймера** будит ядро, и планировщик принудительно снимает поток с ядра.
- Поток может сняться и **раньше** времени — если он сам заблокировался на I/O (ждущий `read()` поток не жрёт CPU, его снимают сразу).
- Приоритет влияет на то, как поток ходит в очереди: `nice`, real-time классы (FIFO/RR) в `SCHED_FIFO`/`SCHED_RR`.

Именно поэтому I/O-задачи выгодно отделять от вычислений: заблокированный на диске/сети поток не мешает остальным.

## Что такое переключение контекста

**Context switch** — это момент, когда ядро снимает один поток с ядра и ставит другой. Механически это «пауза»: процессор — машина состояния, и чтобы вернуть поток к выполнению позже, надо **сохранить всё его состояние** и восстановить состояние следующего потока.

Что именно сохраняется/восстанавливается:

| Компонент | Зачем сохранять |
| --- | --- |
| Регистры процессора (общие) | рабочие переменные текущих вычислений |
| Program Counter (RIP/IP) | с какой инструкции продолжать выполнение |
| Указатель стека (RSP/SP) | адрес стека потока (у каждого потока свой стек) |
| Флаги состояния (RFLAGS) | флаги сравнений/переносов |
| Регистры FPU/SSE (XMM, FPU-состояние) | вещественные вычисления |
| **Режим процессора (user/kernel)** | в каком режиме продолжить выполнение потока |
| MMU/контекст адресного пространства (CR3) | виртуальная память процесса (для потоков одного процесса — общий CR3) |

Ключевой момент, который вы отметили: **режим — часть контекста потока**. Поток всегда начинает и продолжает выполняться в user mode, но внутри syscall'а он «временно уходит» в kernel mode. Если в этот момент его прервут, ядро сохраняет состояние именно в том режиме, где поток находился — обычно приходит из kernel mode (обработчик syscall'а в ядре), и к точке прерывания в ядре.

Важно различать два «переключения»:

- **Mode switch** — переход из user mode в kernel mode и обратно *внутри одного потока* (например, syscall). Контекст потока не меняется, поток тот же.
- **Context switch** — переключение *с одного потока на другой*. Вот тут и происходит полное сохранение состояния, включая режим, в котором каждый поток «застал» процессор.

Проще говоря: при syscall'е поток «ныряет» в ядро и выныривает тем же потоком; при context switch'е ядро снимает один поток целиком (вместе с его режимом, регистрами и стеком) и поднимает другой.

## Цена переключения

Context switch — не бесплатная операция:

- Сохранение/восстановление состояния регистров, стека, FPU.
- **Потеря кэшей** (L1/L2) и TLB: «чужой» поток почти сразу «мажет» кэш, вытесняя чужие данные.
- Нагрузка на планировщик и на системные структуры ядра.
- Частые переключения (квант слишком мал, потоков слишком много) → «пинг-понг» планировщика и падение производительности.

Поэтому в Java и появились потоки-«легковесы» (virtual threads, Project Loom): они позволяют иметь тысячи логических задач, не плодя тысячи потоков ОС и не платя за тысячи context switch'ов.

## Почему это важно для понимания I/O

- **I/O-ожидание часто приравнивается к context switch**: поток, заблокированный на `read()`, снимается с ядра, а когда данные приходят — ядро возвращает его в очередь. Асинхронный I/O (п. 9) уменьшает именно число таких переключений.
- Система с «зависшими» на I/O потоками может показывать высокую загрузку из-за постоянных context switch'ов, а не из-за реальной работы.
- Понимание, что режим — часть контекста потока, объясняет, почему ядро аккуратно «прячет» kernel state между потоками: чужой поток не должен увидеть чужое ядро.

## Практика

```bash
# Сколько переключений контекста делает ваша система (общая статистика)
vmstat 1 5

# Сколько потоков у конкретного процесса
ls /proc/$(pgrep -n java)/task | wc -l

# Сколько раз поток снимался с ядра по своей воле (voluntary) и по принуждению (nonvoluntary)
cat /proc/self/sched

# Состояние потоков: R (running), S (sleeping/ждёт I/O), D (непрерываемый сон — ждёт диска)
ps -o pid,state,comm -e | head
```

Заметный рост `cs` (context switches) в `vmstat` при падающей производительности — типичный признак, что система тратит время на переключения, а не на работу.

## Связь со следующими разделами

- Переключение контекста — реализация планирования потоков, о создании которых шла речь в п. 7.
- Mode switch в syscall'ах связывает эту тему с user/kernel mode (п. 3).
- Асинхронный I/O (п. 9) строится на том, чтобы не блокировать поток и не платить за context switch на каждом `read()`.
